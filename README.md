# CareerVerse AI

Career guidance for students who are confused about applying to jobs.

You upload a resume. The app reviews it, shows which roles it fits, lets you try a short version of the work, and then — if you pick a career — tells you what you’re missing and how to learn it.

Live idea in one line: **resume → “does this fit?” → “what would this job feel like?” → “what should I learn?”**

---

## The problem we kept running into

A resume score is not career advice. Most tools stop at “your resume is 72/100” and a list of buzzwords to add.

That doesn’t help when you’re a student staring at ten similar titles:

- Software Engineer
- Backend Engineer
- Platform Engineer
- ML Engineer
- Data Engineer
- DevOps

They all sound important. The work is not the same. A lot of people apply because the title is familiar, then find out six months later that they hate the day-to-day.

Job descriptions don’t fix this either. They’re written for ATS filters, not for someone trying to imagine Monday morning.

CareerVerse is our attempt to sit in the middle of that mess:

1. Is my resume actually readable?
2. Does it match *this* job, or a job I haven’t thought about?
3. If I sat in this role for a bit, would I want it?
4. If yes, what do I learn first?

## What the app does

You sign up (email or Google), upload a PDF resume, and land on a dashboard. After the resume is in, most modules can be opened on their own. We didn’t want a locked wizard that forces you through everything.

### 1. Resume analysis

The PDF is parsed with PyMuPDF (name, education, skills, experience, projects — whatever we can extract).

Two scores are computed **before** the AI writes anything:

- a resume / content score
- an ATS-style score (keywords, structure, the usual checklist stuff)

Those numbers are generated by rules in code, then handed to the Resume Reviewer agent so it *explains* them instead of inventing new ones. Same resume should get the same scores.

You get:

- overall score
- ATS score
- strengths
- weak spots
- things to change

### 2. Career compatibility

This is resume vs **one** job.

You can:

- upload your own JD (PDF or text)
- or pick from the sample job descriptions we already seeded

The app compares your profile to that role and returns a compatibility percentage, overlapping skills, missing skills, and what to tighten if you care about that job.

### 3. Career Explorer

Compatibility answers “this JD.” Explorer answers “what else?”

Job descriptions are chunked, embedded, and stored in ChromaDB. At match time we embed the resume, pull the most relevant JD chunks, and send *those* to the Career Advisor agent — not a generic “what jobs exist in the world” prompt.

The agent has to recommend roles that actually came back from retrieval. That check is in code, not just in the prompt. We got burned once by the model confidently inventing a role that wasn’t in the uploaded JDs.

You get top 3 matches, each with:

- match %
- confidence
- why it thinks you fit
- a short picture of the role

### 4. Virtual experience

A match percentage is still just a number. This part is meant to feel closer to a tiny intern project than a quiz.

For a recommended career, the Simulation agent builds a short workplace experience: context, a few tasks, decisions, and feedback after you submit. You can go through it and then decide whether to keep that career.

This unlocks after Career Explorer, because we didn’t want people committing to a 3-month plan before they’d seen other options *or* tried the work.

### 5. Choose a career → skill gap

When you pick a role, we compare your resume to that career (not to every job on the internet).

You get:

- skills you already have
- missing technical skills
- missing soft skills
- a readiness score
- what to do next

### 6. Learning roadmap

Same chosen career. The Learning Plan agent turns the skill gap into a 3-month plan. The point is not “here are 40 random courses.” It’s “here’s a path for *this* role.”

### 7. Career mentor

A chat that stays open on the side. You can ask about the resume, a match, a missing skill, or interview stuff without leaving the page you’re on.

It already has your resume and whatever you’ve generated so far, so it doesn’t go hunt through ChromaDB again. Streaming, so it doesn’t sit there silent for 20 seconds.

## How a session usually goes

```
Landing → Login / Signup
        → Upload resume (PDF)
        → Resume analysis
        → Career compatibility   (optional, your JD or a sample)
        → Career Explorer        (top 3 roles)
        → Virtual experience
        → Choose this career
        → Skill gap
        → Learning roadmap
```

Explorer / compatibility / analysis don’t depend on each other. Virtual experience needs Explorer first. Skill gap and roadmap need a chosen career.

## How it’s built

We kept a boring rule that saved us a lot of pain: **routes don’t talk to the LLM. Services don’t either. Only agents do. Prompts live in their own folder.**

When an answer came back weird, we could tell quickly whether we asked the wrong thing (prompt) or fed it the wrong context (retrieval / parsing).

```
React frontend
      │  JWT
      ▼
FastAPI routes          backend/app/api/
      │
      ▼
Services                parse PDFs, ATS scores, save rows, run RAG
      │
      ▼
Agents                  backend/app/agents/     ← only place that calls OpenRouter
      │
      ▼
Prompts                 backend/app/prompts/
```

### The AI pieces

There are six agents. They all go through one shared OpenRouter client (`openrouter_client.py`). Default model: `meta-llama/llama-3.1-8b-instruct`.

| Agent | Job |
| --- | --- |
| Resume Reviewer | Explain the precomputed scores, write the review |
| Career Advisor | Compatibility + top 3 explorer matches, grounded in retrieved JDs |
| Simulation | Virtual experience tasks |
| Skill Gap | Missing skills for the chosen role |
| Learning Plan | 3-month roadmap |
| Career Mentor | Streaming chat |

We originally pointed this at OpenAI. Billing got in the way mid-build, so LLM calls moved to OpenRouter. Embeddings stayed on Gemini’s embedding model. The client is shared on purpose so swapping a model is an env var, not a rewrite of every agent.

### RAG (only for job descriptions)

Career matching is the one place we didn’t want the model “remembering” what a Backend Engineer usually needs.

1. JD is uploaded or a sample is selected
2. Text out with PyMuPDF
3. Split into ~500-token chunks with a little overlap
4. Embed with Gemini `gemini-embedding-001`
5. Store in ChromaDB (`job_descriptions` collection) with ids / role title / chunk index
6. Resume gets embedded
7. Top-k similar chunks come back
8. Career Advisor is only allowed to talk about those JDs

Resume review, mentor chat, skill gap, and roadmap do **not** go back to Chroma for a second opinion. By then we already have structured data in the database.

### Auth and data

- Email/password → JWT in localStorage (simple, not perfect)
- Optional Google sign-in. Backend verifies the ID token. Frontend and backend must use the same client ID.
- Resumes, reports, matches, simulations, skill gaps, roadmaps, mentor messages → SQLite locally, Postgres if `DATABASE_URL` is set
- PDFs → `uploads/`
- Vectors → `vector_db/`

Identical resume PDFs are hashed so we don’t re-run the reviewer for the same file.

## Stack

| Part | Choice |
| --- | --- |
| Frontend | React, TypeScript, Vite, Tailwind, Framer Motion |
| Backend | FastAPI + Uvicorn |
| App DB | SQLite (local), PostgreSQL (production via `DATABASE_URL`) |

| Embeddings | Gemini `gemini-embedding-001` |

Frontend talks to the backend through one helper (`frontend/src/services/api.ts`) and `VITE_API_URL`. Nothing else should hardcode localhost.

## Run it locally

Two terminals. Backend first.

### Backend

```bash
cd backend
python -m venv venv

# Windows
venv\Scripts\activate
# macOS / Linux
source venv/bin/activate

pip install -r requirements.txt
```

Copy `backend/.env.example` → `backend/.env` and fill in:

- `OPENROUTER_API_KEY`
- `GEMINI_API_KEY`
- `JWT_SECRET`

Leave `DATABASE_URL` blank for SQLite.

```bash
python -m uvicorn app.main:app --reload
```

- API: http://localhost:8000
- Docs: http://localhost:8000/docs
- Health: http://localhost:8000/health → `{"status":"ok"}`

### Frontend

```bash
cd frontend
npm install
```

Copy `frontend/.env.example` → `frontend/.env`:

```
VITE_API_URL=http://localhost:8000
VITE_GOOGLE_CLIENT_ID=
```

If you want Google login, put the same client ID in both env files, and add `http://localhost:5173` under Authorized JavaScript origins in Google Cloud.

```bash
npm run dev
```

App: http://localhost:5173

## Environment variables

Don’t commit `.env` files. Examples are placeholders only.

**Backend**

| Name | What it’s for |
| --- | --- |
| `OPENROUTER_API_KEY` | Every agent / LLM call |
| `OPENROUTER_MODEL` | Defaults to Llama 3.1 8B Instruct |
| `OPENROUTER_REFERER` | Your frontend URL |
| `OPENROUTER_APP_NAME` | Shown to OpenRouter |
| `GEMINI_API_KEY` | JD embeddings only |
| `JWT_SECRET` | Sign login tokens |
| `GOOGLE_CLIENT_ID` | Google login (optional) |
| `CORS_ORIGINS` | Allowed frontends, comma-separated |
| `DATABASE_URL` | Empty = SQLite. Postgres in production |
| `CHROMA_PERSIST_DIR` | Defaults to `../vector_db` |
| `UPLOAD_DIR` | Defaults to `../uploads` |
| `ENVIRONMENT` | `development` locally, `production` on Render |

`SUPABASE_URL` / `SUPABASE_KEY` exist in config but nothing uses them yet. Files are still local.

**Frontend**

| Name | What it’s for |
| --- | --- |
| `VITE_API_URL` | Backend base URL |
| `VITE_GOOGLE_CLIENT_ID` | Same Google client as the backend |

## Deploy (what we actually used)

- Frontend → Vercel, root directory `frontend`, build `npm run build`, output `dist`
- Backend → Render Web Service, root directory `backend`, start `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
- Set `VITE_API_URL` on Vercel to the Render URL
- Set `CORS_ORIGINS` on Render to the Vercel URL **and** `http://localhost:5173`
- Production needs `DATABASE_URL` pointing at Postgres. Render’s disk is wiped on deploy, so SQLite / `uploads/` / `vector_db/` will not last

## What this is not

It’s not a job board. It doesn’t apply for you. It doesn’t scrape LinkedIn. It won’t stay accurate if the only JDs in Chroma are the samples — Explorer is only as good as the descriptions you give it.

It’s a student project: upload a resume, get a honest-ish read, try a role on for size, then get a plan if you pick one.
